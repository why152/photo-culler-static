# Photo Culler 静态前端迁移规格

**Status:** ready-for-agent

## Problem Statement

Photo Culler 目前以本机 Flask 和 Python 图像、SQLite、文件操作运行时提供浏览器界面。用户需要把它部署到纯前端服务器，同时保留本地照片不上传、JPEG-first 的保守初筛、完整照片组的可恢复移动和恢复能力。部署后的应用不能依赖 Python、Flask、本机 HTTP API 或本机 MLX 模型。

## Solution

交付一个由 HTTPS 静态服务器托管的普通前端站点。正式支持 macOS 的 Chrome 和 Edge；用户在页面中明确选择本地照片目录并授权读写。浏览器直接枚举目录、只解码 JPEG 作为分析源、在浏览器 worker 中完成保守技术初筛、在 IndexedDB 中保存界面进度和缓存，并在目标照片目录内写入 movement journal 来执行、发现和恢复 review batch。照片字节、目录名称、分析结果和筛选进度不发送到服务器。页面不是 PWA，也不提供 AI 二次判断。

## User Stories

1. 作为摄影者，我想从 HTTPS 静态网页选择一个本地照片目录，以便不安装或启动 Python 应用也能开始筛选。
2. 作为摄影者，我想在授权前知道网站会请求该目录的读取和写入权限，以便自己决定是否允许文件操作。
3. 作为摄影者，我想只选择普通照片目录，以便不会把一个既有 review batch 当成照片来源。
4. 作为摄影者，我想扫描一层目录并只将含 JPEG 的项目显示为 photo group，以便 RAW-only 文件不被误处理。
5. 作为摄影者，我想让同 stem 的 JPEG、RW2 和 XMP 始终构成一个 photo group，以便不会拆散相机原件和侧车文件。
6. 作为摄影者，我想只把 analysis source JPEG 解码，以便 RAW 不被读取、改写或用于自动判断。
7. 作为摄影者，我想看经 EXIF 方向校正的缩略图和全图，以便不必离开筛选界面。
8. 作为摄影者，我想得到保守的 keep、review、reject 初筛，以便只有明显技术问题被建议移出。
9. 作为摄影者，我想让全黑、全白、低清晰度和无法读取的 JPEG 留在 review，以便不把不确定图像自动当作废片。
10. 作为摄影者，我想在分析不阻塞界面的情况下看到进度，以便大目录仍可继续操作。
11. 作为摄影者，我想以 pick、keep、reject 记录 review decision，以便人工判断与文件动作保持分离。
12. 作为摄影者，我想通过现有键盘与筛选交互浏览 photo group，以便连续审核效率不下降。
13. 作为摄影者，我想保存当前选择、筛选条件、候选和 review decision，以便刷新或重新打开站点后可以继续审核。
14. 作为摄影者，我想在重新打开站点后重新授予目录权限，而不是让网页在未获授权时访问照片。
15. 作为摄影者，我想把已标记 photo group 移到同目录的 review batch，以便原目录立刻只保留未移出的照片。
16. 作为摄影者，我想在移动前得到明确的组数和文件数，以便确认实际范围。
17. 作为摄影者，我想在移动时看到组与成员的进度，以便长操作的状态可见。
18. 作为摄影者，我想在每个成员动作后更新 movement journal，以便关闭标签页或操作异常后仍能判定恢复状态。
19. 作为摄影者，我想拒绝覆盖已有同名文件，以便恢复或移动不会破坏后来放入的照片。
20. 作为摄影者，我想在再次选择源目录后发现已完成或中断的 review batch，以便恢复不依赖当次浏览器会话。
21. 作为摄影者，我想查看每个 review batch 中的照片预览，以便核对被移出的内容。
22. 作为摄影者，我想恢复完整 review batch，以便撤销一次批量移动。
23. 作为摄影者，我想从 review batch 恢复单个完整 photo group，以便保留其余批次不变。
24. 作为摄影者，我想让恢复也拒绝覆盖源目录中后来出现的同名文件，以便避免静默丢失。
25. 作为摄影者，我想在浏览器不支持所需本地目录能力时看到明确提示，以便不会误以为文件已被分析或移动。
26. 作为摄影者，我想让静态服务器只交付网页资源，以便没有照片内容或服务端 API 可以被上传或调用。
27. 作为维护者，我想部署一个可直接静态托管的目录，以便不维护 Python 环境、端口或后端进程。
28. 作为维护者，我想有复制照片目录的自动化浏览器验证，以便证明原始照片目录不会被测试写入。
29. 作为维护者，我想从仓库中移除 Flask、Pillow、OpenCV Python、SQLite 和 MLX 运行时，以便“完全前端化”可由依赖和代码审计验证。
30. 作为维护者，我想让部署说明注明 Chrome/Edge、HTTPS 和本地权限边界，以便用户不会把 Safari、Firefox 或不安全 HTTP 当作受支持配置。

## Implementation Decisions

- 普通静态单页应用，而非 PWA；构建结果由任意 HTTPS 静态服务器提供，运行时没有后端 API。
- 支持范围是 macOS Chrome 和 Edge。应用启动时检测目录选择、可写文件、目录枚举和文件移动能力；缺少任一能力时停止在说明页。
- `Review Workspace` 是唯一高层操作边界。它拥有目录授权、扫描、分析、筛选记忆、review batch 发现、移动和恢复；界面通过该边界更新状态，不包含文件系统协议。
- 在每次新会话和页面恢复时重新检查目录 handle 的读写权限。可持久化 handle 的引用只能用于请求用户重新授权，不能绕过权限提示。
- photo group 由同 stem 的 JPEG、RW2、XMP 成员组成；analysis source 是其中 JPEG。目录扫描保持非递归，并排除 review batch 目录。
- 图像解码、缩略图生成和技术评分在 worker 内执行。评分保留当前保守分类语义；移植后以基准副本验证阈值和分类，不把评分作为审美或自动删除判断。
- 分析结果、缩略图和 review decision 使用 IndexedDB 的版本化缓存。缓存的失效键使用浏览器可读的文件名、大小和最后修改时间；磁盘 journal 才是移动恢复的权威记录。
- 移动先创建目标 review batch 和 journal，然后以完整 photo group 为单位移动成员、在每个成员后更新记录。任何失败都保留可发现的 journal 和已完成成员，不进行静默清理。
- 恢复按 journal 的反向记录进行；在任何目标位置已存在同名文件时失败并保留原状。最后一个成员恢复后才移除空 review batch 与 journal。
- 现有实验性本机 AI 二次判断不迁移，也不替换为云端请求或远程模型。
- production 站点不接收照片、文件路径、缩略图、分析结果或 review decision。所有请求只获取同源静态前端资源。

## Testing Decisions

- 测试关注 `Review Workspace` 的可观察行为，不断言私有实现细节或特定浏览器内部存储布局。
- 单元和集成测试覆盖 photo group 组成、保守分类、缓存失效、journal 状态机、碰撞拒绝、失败恢复及完整/单组恢复。
- 浏览器端到端测试在 Chrome 或 Edge 中运行，对带有测试标记的复制目录执行选择、扫描、键盘审核、移动、刷新后发现 journal、完整恢复和单组恢复。
- 每一轮写操作测试都验证真实来源目录的文件内容和修改时间未变；测试只写入复制目录。
- 静态部署验证使用静态服务器提供构建目录，并确认应用没有对照片建立网络请求或 HTTP API 调用。
- migration completion audit 检查仓库中不再存在 Python/Flask/MLX 运行时代码或生产依赖，且 README 的运行与安全边界和实现一致。

## Out of Scope

- Safari、Firefox、移动端和非 HTTPS 的正式支持。
- RAW 解码、RAW 技术评分、递归目录扫描、审美排序、自动永久删除。
- PWA 安装、Service Worker 离线缓存、账户、同步、服务器端照片处理与云端 AI。
- 实验性的本机 MLX AI 二次判断及任何远程替代。

## Further Notes

浏览器文件系统权限由用户授予并可能在页面关闭或浏览器设置变更后失效。重新选择或重新授权目录是预期流程；review batch 与 movement journal 仍在照片目录内，因此恢复记录不依赖浏览器缓存。
